## 0. 摘要

三份外部建议（qwen / workbuddy / workbuddy的转述版）在**方向**上高度一致：先修评估层，再谈模型。方向是对的，但：

1. **它们都严重低估了仓库里已经存在的资产** —— 6.2 万场带完整收盘价的比赛躺在磁盘上，全仓库没有一行代码读过那些赔率列。
2. **它们引用的关键数字有 6 处经不起复核**，包括 qwen 的 RPS 结论和联赛异质性结论（符号是反的）。
3. **它们都没有发现系统当前实际在跑什么** —— 实测有效模型权重是 6.25%，不是配置里写的任何值。

核心判断：**这个项目当前的产出 ≈ 93.75% 的去水市场 + 6.25% 一个比市场更差的模型 + 5 步手工微调。** 在这个结构下讨论"融合权重该给模型多少"是无意义的，因为无论给多少，结论都由"模型是否优于市场"决定，而它不优于。

而真正的深，不在模型层，在**把 6.2 万场收盘价接进来**——那才是能把样本从 955 变成 62,347 的唯一杠杆，也是能把"有没有 edge"这个问题从信念问题变成统计问题的唯一路径。

## 2. 复算结果：三份文档的 6 处硬错误

我直接用 `review_ledger.jsonl` 重算（955 行，`chain=None` 426 行 / `chain=v2` 529 行）。

### 2.1 ✅ qwen 对的部分

**Brier 配对检验完全复现**：

```
配对样本 n = 483
  mean final  = 0.5667
  mean market = 0.5631     (market_fair 三项和 = 1.0000，确认已去水)
  Δ = +0.0036   配对 t = +0.969   |t| < 1.96，不显著
  逐场：模型更好 243 场 / 市场更好 240 场 / 平 0
```

qwen 写的 Δ=+0.0036、z=+0.97、243/240 —— **一字不差**。`upgrade_tracker` 的 "IMPROVED z=3.14" 确实是 vs legacy（0.6172）而非 vs market。

### 2.2 ❌ qwen 错的部分

**(a) RPS 结论是配对口径错误。**

qwen："RPS（全 955 场）0.1907 vs 0.1936 微弱占优"

实测：`rps_final=0.1907` 是 **n=529**，`rps_market=0.1936` 是 **n=483**。两个不同样本相减。

配对到同一 483 场后：

```
RPS paired n=483: final 0.1946 vs market 0.1936
RPS Δ = +0.0010   t = +1.120
```

**配对后模型在 RPS 上也略差。** 这和 workbuddy 批评"巴甲命中率 31.6% vs 市场 63.2%"是同一类错误——qwen 在自己的 RPS 那一行犯了它批评别人的错。

**(b) 联赛异质性结论符号反了。**

qwen："西甲 Δ-0.068、葡超 Δ-0.055、欧国联 Δ-0.016（final 显著优于市场）"

实测（v2，Δ = final − market，**负 = 模型更好**）：

| 联赛 | n | Δ (v2) | Δ (全 955) | 实际 |
|---|---|---|---|---|
| 西甲 | 41 | **+0.0039** | +0.0108 | **模型更差** |
| 葡超 | 12 | **+0.0101** | +0.0387 | **模型更差** |
| 欧国联 | 50 | −0.0002 | −0.0002 | 基本持平 |

qwen 点名的三个"跑赢市场"的联赛，实测全部是**跑输或持平**。这条 Phase 5 论据不成立。

**(c) odds_series "每半小时快照"不成立。**

qwen："871 个赔率时序文件（8月至今，每半小时快照）"

实测：871 个文件共 **2,836 个快照，平均每场 3.3 个**；158 场只有 1 个快照（算不了 CLV），713 场（81.9%）有 ≥2 个。调度器设计了半小时一次，实际覆盖率约 1/15。

### 2.3 ❌ upgrade_tracker.py 有三个叠加的记账 bug

`scripts/upgrade_tracker.py:117`：

```python
"v2_vs_market_same_period": mkt,     # mkt = market_summary(v2)
```

`market_summary()` 返回的是**市场的 Brier**，键名却读起来像"v2 的分数"。于是：

```
tracker 记录:  v2_vs_market_same_period.brier = 0.5631
实际           final  = 0.5667   ← 模型自己的分
               market = 0.5631   ← 0.5631 其实是市场
```

三个问题叠加：

1. **`verdict: "IMPROVED"` 来自 `paired_vs_legacy`（vs 旧链），不是 vs 市场** —— qwen 指出过；
2. **`v2_vs_market_same_period` 填的是市场自己的分**，任何人读这个键都会得出"v2 赢市场 0.02"的错误结论；
3. **`market_reference` (0.5834) 和 v2 市场 (0.5631) 是两个不同子集**（364 行 legacy vs 483 行 v2），把它们相减本身就是无效比较。

**结论：upgrade_tracker 是这个项目里最危险的单个文件。** 它是 PR#4 自动 agent 用来做 ACCEPT/REJECT 判定的输入之一。它现在正在系统性地把"没赢"报成"赢了"。

### 2.4 ❌ workbuddy 建议的 Kelly 降幅已经做完了

workbuddy 第 6.5 条："Kelly 降到 1/4，注码改用 p 的 10% 分位数"。

`config/strategy.json` 实测：`"kelly_fraction": 0.25` —— **已经是 1/4**。
`"activation_mode": "shadow"` —— 系统还处于影子模式。

这条建议作废。但"注码改用后验分位数"那半条仍有效（Kelly 对 p 的误差敏感性是真的），且成本很低。

### 2.5 ✅ workbuddy 对的部分（且我用数据确认了）

workbuddy 引用了竞彩 overround 约 1.08–1.15（来源是占位符 citation，无法核）。我直接从 871 个时序文件的 2,836 个快照算出真实值：

```
竞彩胜平负 overround:
  中位数 1.1212   均值 1.1204   P10 1.1103   P90 1.1277
  → 理论返还率 89.2%，抽水约 12.1%
  盈亏平衡所需相对定价优势 ≈ 12.1%（相对市场公平概率）
```

**落在 workbuddy 估计区间的中部，战略结论成立且比它说得更硬：**

- 竞彩价格下，你的模型需要有 **12.1% 的相对定价优势**才谈得上盈亏平衡；
- 系统实测的概率优势（Brier Δ = 0.0036 / 市场 0.5631 ≈ **0.64% 相对优势**）；
- **差距是 19 倍。**

这不是"edge 还不够大"，这是"edge 不存在，但成本是刚性的"。

（另注：串关会把抽水复利放大，workbuddy 这条也对。）

## 3. 系统实际上在跑什么（两份文档都没查）

### 3.1 三套不同的权重

| 来源 | model | market | djyy | 谁在读 |
|---|---|---|---|---|
| `config/prediction.json` | 0.10 | 0.60 | 0.30 | 兜底默认值 |
| `data/state/fusion_weights.json` champion | **0.05** | **0.75** | **0.20** | **生产推理实际使用** |
| `ablation_report.json` meta.weights | 0.10 | 0.75 | 0.15 | 消融回放 |

`engine/main.py:319-321` 确认生产路径读的是 champion：

```python
_champion = _fusion_opt.get_champion()
fusion_cfg["model_weight"] = _champion.model      # 0.05
fusion_cfg["market_weight"] = _champion.market    # 0.75
fusion_cfg["djyy_weight"] = _champion.djyy        # 0.20
```

### 3.2 DJYY 已经死了 2 个月，但还挂着 0.2 的权重

ledger 实测：

```
legacy (n=426, 07-19..08-28):  djyy_prob 非空 = 123    最后出现 2026-08-15
v2     (n=529, 08-29..10-09):  djyy_prob 非空 = 0      ← 529 场全部为空
```

DJYY 数据源在 8 月中旬停止。v2 链从 8-29 开始，此后 **529 场没有一场有 DJYY 概率**，但配置仍给它 0.2 权重。

### 3.3 有效权重 = 6.25% 模型

`engine/prediction/fusion.py:136-142` 在 djyy 为空时走 `fuse_two_way`，并**重新归一化**：

```python
total_w = mw + kw
mw, kw = mw / total_w, kw / total_w
```

代入实际 champion：

```
有效 model  = 0.05 / (0.05 + 0.75) = 0.0625
有效 market = 0.75 / (0.05 + 0.75) = 0.9375
```

**模型在整个融合里的边际贡献是 6.25%。**

### 3.4 而模型比市场差

v2 实测：

```
brier_model  = 0.5925  (n=529)
brier_market = 0.5631  (n=483)
brier_djyy   = 0.6460  (legacy n=123，全系统最差)
```

把一个比市场差 0.029 的模型按 6.25% 混进市场：

```
0.9375 × 0.5631 + 0.0625 × 0.5925 = 0.5649
实测 brier_final = 0.5667  （差额来自 5 步 post_fusion）
```

**预测误差方向、数量级全部对上。**

### 3.5 优化器自己的结论印证了这一点

`ablation_report.json` 的 `weight_search.best_weights`：

```json
{"model": 0.0, "market": 0.6, "djyy": 0.15}
```

**优化器搜出的最优解，模型权重是 0。** 它被 REJECT 只因为 `t=1.64 < min_z=1.96`。

所以"37 个候选全被 REJECT"不是优化器没 power——是**它唯一想试的那个方向（把模型权重压到 0）需要 20% 以上的样本改善才够 1.96，而 6% 的权重本来就只能产生 0.3% 的改善**。门槛与可及效应量不匹配，导致所有候选必然 REJECT。这是阈值设计问题，不是优化问题。

### 3.6 小结

```
final ≈ 0.9375 × 去水市场 + 0.0625 × (更差的模型) + 5 步手工微调
```

这解释了三份文档里所有的困惑：为什么 Brier 贴着市场、为什么优化器推不动、为什么"IMPROVED"是假的、为什么模型做得再深也不会有变化。

**在这套结构下，12 步融合链不是"深度"，它是噪声发生器。** 它的每一步都在一个 6.25% 的基底上做 ±0.02 量级的手工调整，而这些调整的效应量（~0.1%）小于 ablation 回放的噪声（t 检验在 n=171 下的分辨率约 0.3%）。

## 4. 我的独立主张：怎么做深

三份文档都同意"Phase 4/Phase 3 = 残差建模"。我同意，但认为**顺序完全错了**，而且它被放在了一个它无法被验证的位置上。

### 4.1 先纠正一个目标定义

两份文档在"北极星"上打架：qwen 说换成 CLV，workbuddy 说 RPS/log-loss vs 去水市场。

**workbuddy 对，qwen 错。** 理由是 CLV 只在"实际下注"的定义域上存在——系统两个月下了 34 注，RPS 每场都有。换成 CLV 等于把主指标更新频率从每场一次降到几个月一次。

但 workbuddy 的 RPS 首选也不该盲从。用你们已有的 483 场配对差做一次**功效分析**：给定真实效应量，RPS 和 log loss 各需要多少样本才达到 1.96。你们真实 RPS Δ = +0.0010，配对 SD 下 t=1.12。用这个实测方差反推，**在 RPS 上永远达不到显著**，而 log loss 的方差结构不同，很可能先到。

**这件事半小时能做完，不要靠吵。**

正确的分层是：

| 层 | 问题 | 指标 | 评估对象 |
|---|---|---|---|
| 概率层 | 概率准不准 | de-vigged paired log loss（主）/ RPS | 每场预测 |
| 决策层 | 下注划不划算 | CLV + ROI（配对） | 实际下注 |

**两者并列，永不互替。** 不要设一个"全局北极星"。

### 4.2 真正的深：把样本从 955 变成 62,347

这是整个项目**唯一一个能把"有没有 edge"从信念问题变成统计问题的动作**，而且数据已经在硬盘上。

关键在于历史数据自带的东西比想象的多：

| 特征 | 数据来源 | 是否可用 |
|---|---|---|
| 去水收盘 1X2（多公司均值） | AvgCH/CD/CA | ✅ |
| **开盘 1X2** | AvgH/D/A | ✅ |
| **盘口移动 = 开盘→收盘变化** | 上两行之差 | ✅ **← 最强信号，目前完全未用** |
| 收盘亚盘让球线 | AHCh/AvgCAHH | ✅ |
| 收盘大小球 2.5 | AvgC>2.5 | ✅ |
| 跨公司分歧 | MaxC − AvgC | ✅ |
| Elo / 攻防强度（从比分重建） | FTHG/FTAG 全历史 | ✅ 无泄漏（按日期排序） |
| 射门（xG 代理） | HS/AS/HST/AST | ✅ 42,423 场 |
| 半场比分 | HTHG/HTAG | ✅ 42,426 场 |
| 红黄牌、裁判 | HY/AY/HR/AR | ✅ |
| 伤停、DJYY | — | ❌ 历史上没有 |

**盘口移动（open→close）是 closing line efficiency 文献里最稳健的单一信号**，而它天然就在这个数据集里，因为每个价格点都同时有开盘和收盘两份。现有系统 `odds.csv` 只有单一价格，把这个信号彻底丢掉了。

### 4.3 残差建模的精确形式

两份文档都写 `p_final = p_market_devig + r̂(features)`，方向对，但要落到能跑的形式：

**不要学 `r = y − p_market`。** y 是 0/1 硬标签，一场比赛 3 bit 信息，直接回归会被噪声淹没。

正确做法：

```
1) 用 DC + MC 在历史数据上重建每个时点的比分矩阵（严格 walk-forward）
2) 得到每个时点的模型概率 p_model(t)
3) 目标：p_market_devig(t) − p_model(t)   ← 市场相对模型的偏离
4) 训练 f_θ 预测这个偏离，输入特征 = 
     [开盘-收盘盘口移动, 跨公司分歧 MaxC-AvgC,
      Elo 分歧, 休息日/赛程密度, 联赛 one-hot, 亚盘+大小球方向一致性]
5) p_final = p_model(t) + λ · f̂_θ(features)，λ 由内层时间窗拟合
```

两个必须遵守的纪律：

- **λ 由内层时间窗拟合，外层测试期只跑一次**（`engine/backtest/ts_split.py` 已有这套设施，目前没有实验真正用起来）
- **`λ=0` 必须是候选之一**，且 λ=0 即"完全相信市场"。如果 λ 的最优值是 0，结论是"模型无边际信息"，这是一个**完整且可发表的结论**，不是失败

### 4.4 跨盘口一致性应该被提前

workbuddy 把它放在 B4 / P1。我认为它应该更靠前，理由是它**不依赖扩样本就能跑**，而且它检验的是模型内部一致性，不是市场预测能力：

```
用同一个比分矩阵给 1X2 / 亚盘 / 大小球 / 双方进球全部定价
   ↓
要求同一场比赛多盘口信号方向一致
   ↓
不一致的部分 = 模型内部矛盾 = 噪声，应被剔除
```

在只有竞彩一个市场（`market_isolation.py` 已预留 `benchmark_closing_*` 字段但没用）的情况下，这套做不了；接上 football_data 的 33,061 场亚盘+大小球收盘后立刻可做。

它还有一个副作用价值：**跨市场不一致的样本是最有诊断价值的样本**，人工看 20 场比看 200 场有效。

## 5. 路线图：门禁在第 3 周

我把它设计成"每一步的产出决定下一步是否值得做"，而不是排期表。

### Phase 0 · 把尺子修对（1 周，零建模）

| # | 动作 | 验收 |
|---|---|---|
| 0.1 | **修 `upgrade_tracker.py` 三个记账 bug** | 键名与值语义一致；`v2_vs_market` 必须是差值不是分值 |
| 0.2 | **权重单一真源**：config / fusion_weights.json / ablation 三处合一 | 运行时权重与落盘权重逐场可追溯 |
| 0.3 | **落盘有效权重**（归一化后的真实 model/market 比例） | 每条预测记录里能看到 effective_model_weight |
| 0.4 | **DJYY 死源处理**：0 命中时权重归零或告警 | 529 场 v2 的回放必须与账本逐场一致 |
| 0.5 | 修 `favorite_band` 执行层（odds<1.8 应当 stake=0，但 ev_report 仍在记账） | 记账口径 = 下注口径 |
| 0.6 | PR#3 合并（qwen 的判断我同意），合并后重置基线 | 忠实率 ≥95% |

**0.1 是这周唯一不可跳过的。** 它是自动 agent 的判定输入。

### Phase 1 · 接 6.2 万场收盘价（2 周）

- 建 `engine/backtest/historical_replay.py`，消费 football_data
- 严格 walk-forward（用 `ts_split.py`）
- 输出：league-season 分层的 paired log loss vs 去水收盘

## 6. 多 agent 治理：两份文档各管一半，缺 portfolio 层

qwen 的 `docs/EXPERIMENTS.md` 实验登记表 和 workbuddy 的 `PROPOSAL.md` **不重复，是互补的**：

- `PROPOSAL.md` 管**单次实验**的预注册（假设/主指标/失败判据/回滚）
- `EXPERIMENTS.md` 管**跨 agent 的多重比较**（撞车、防重复、portfolio 级 FDR）

缺的那一层是 workbuddy 自己的论证的直接推论：它说闭环会朝"指标好看"进化，但防护只到"单个 PR 必须附反事实对照"。**如果 agent-A 跑 50 个假设、agent-B 跑 50 个，各取最好的那个报上来，多重比较照样骗过去。**

需要在两份之外加的：

| 规则 | 内容 |
|---|---|
| portfolio 登记表 | 每个实验登记 hypothesis/branch/metric/判定日，**对自动 agent 只读可追加、不可删改**（配 hash chain） |
| portfolio FDR | 跨 agent 汇总检验用 BH-FDR，不用各自的 p 值 |
| 派生数据隔离 | `data/state/**` 只读之外，**每个 agent 的分析产物写到自己分支专属目录**——否则代码不冲突、派生数据照样冲突 |
| kill rule | 预注册只管"成不成立"，不管"失败怎么退出"。没有清理路径的实验会永久留在 config 里污染下一个实验 |
| 仲裁人 | B 的 CLV 报告和 C 的回放结论矛盾时谁说了算 |

另两条 workbuddy 提得对：同时不超过 3 个写 agent（review 带宽是真瓶颈）；分支生命周期 ≤1 周。
