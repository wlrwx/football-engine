## 2. DJYY 能不能修 —— 能

### 数据源本身没有任何问题

| 检查项 | 结果 |
|---|---|
| `djyylive.com` | HTTP 200，正在服务当日赛程 |
| `/api/leagues/fixtures` | 181 场，**181/181 带 `_djyy_id`** |
| `/api/match/{id}/comparison` | 正常返回 `p_home/p_draw/p_away`，三项和 = **1.0000** |
| 连续 12 次快速请求 | 全 200，**无限流**（排除速率限制假设） |
| 本地生产链路 | **6/6 场拿到 `model_probs`** |

### 真正断在客户端两处（已修）

**缺陷 A：时间预算固定 180s，假设每接口 1.5s——实测 5.4s。**

原注释写着"30场×4接口, 180s 足够"。这个"足够"是错的：

```
实测：6 场耗时 130.5s → 21.8s/场 ≈ 5.4s/接口
180s 预算 → 只够 8 场
账本实测：日均 12.1 场、峰值 30 场
     → 典型日丢 33%，峰值日丢 73%，且 break 是静默的
```

**这个缺陷与 CI 无关，在本地同样存在。**

**缺陷 B：所有失败路径都静默。** `fetch_fixtures` 返回 0 → `return {}`，无告警、无退出码、无状态文件。

**连带后果：** DJYY 死了 2 个月，`config` 仍挂着 `djyy_weight=0.20`，而 `fusion.py:136-142` 会把权重重新归一化 → **运行时有效权重变成 model 6.25% / market 93.75%**。账本里 `djyy_prob` 长期为 null，零告警。

**顺带抓到一个潜伏 bug**：`info` 只在"预算未耗尽"分支内赋值，但函数末尾无条件引用它 → 预算一过即 `NameError` → 被 `except` 吞掉。（是我写的测试抓出来的。）

### 修复效果（实测）

| | 修复前 | 修复后 |
|---|---|---|
| 每场耗时 | 21.8s | **12.2s**（提速 44%） |
| 180s 能覆盖 | 8 场 | 自适应：12 场→288s，30 场→720s |
| 失败可见性 | 静默 | `data/state/djyy_status.json` + 显式告警 |

新增环境变量：`DJYY_ENRICH_MIN_BUDGET_S` / `DJYY_ENRICH_SEC_PER_MATCH` / `DJYY_ENRICH_MAX_BUDGET_S` / `DJYY_FETCH_LINEUPS`（阵容默认关，store-only 不参与任何概率计算却占 1/4 接口）。

### 仍需你操作：CI 侧

`manager.py:400` 已有人（2026-10-10）写了「本地正常 / CI 为0」的诊断。
代码链路现在正常，且本地无限流，所以剩下的只能是网络可达性差异。
最可能是自建边缘 Worker 对 GitHub Actions 数据中心 IP 的误伤。

详见 **《DJYY修复指引.md》**，给了两条路（Cloudflare WAF Skip 规则 / 共享密钥 header）+ 存活探针配置。

## 5. 决定性结果：模型层是净负贡献

### 市场基准（33,060 场，2017-07 ~ 2026-08，14 联赛）

| 指标 | 值 |
|---|---|
| Brier | 0.58388 |
| logloss | 0.9802 |
| RPS | 0.19827 |
| **overround 均值/中位** | **1.0568 / 1.057** |

对比竞彩实测 overround **1.1212**——**欧洲盘 5.7% vs 竞彩 12.1%，差 2.1 倍**。

市场 argmax 校准良好：40分档→0.417(n=1469)、50→0.502(n=909)、70→0.750(n=328)、80→0.801(n=181)。

### walk-forward DC vs 市场（严格时间切分，187 次重拟合，41,668 条预测）

| 指标 | 模型 | 市场 | Δ | t |
|---|---|---|---|---|
| Brier | 0.59993 | 0.58388 | **+0.01604** | **+21.90** |
| logloss | 1.00452 | 0.9802 | +0.02432 | +21.83 |
| RPS | 0.20562 | 0.19827 | +0.00735 | +21.55 |

逐场：模型更好 14,833 / 市场更好 18,227。

**14 个联赛全部 FDR 校正后显著更差**，Δ 从 +0.0124（G1 希腊超）到 +0.0233（T1 土超），无一例外。

### 这个结果解释了系统过去两个月的所有困惑

| 观察 | 解释 |
|---|---|
| Brier 贴着市场（Δ=+0.0036, n.s.） | final ≈ 0.9375×市场 + 0.0625×更差的模型 |
| 37 个权重候选全 REJECT | 任何朝模型方向的移动都在制造损失 |
| 优化器 `best_weights = {model: 0.0}` | **它唯一的直觉是对的**，只因 t=1.64<1.96 被拒 |
| "IMPROVED" vs legacy | 修 bug 有效果，但与 edge 无关 |

**结论：在当前证据下，模型层应当取 0 权重。**
配置里的 `model_weight=0.05 / djyy_weight=0.20` 是未经验证的先验，
而 `djyy` 更是完全失效的死权重。

## 6. 新发现：L3 闸门缺口

`ev_report` 原本对**全部预测**算 ROI，而下注侧 `main.py:1029` 的
`favorite_band_factor` 把 odds<1.8 直接乘 0。**两套口径脱节。**

修复后拆开看：

| 赔率层 | 反事实（全部预测） | 闸门后可下注 |
|---|---|---|
| L1 大热(<1.5) | n=284, ROI −5.4% | **闸门禁投** |
| L2 热(1.5-1.8) | n=218, ROI −13.6% 送钱区 | **闸门禁投** |
| **L3 中(1.8-2.2)** | **n=243, ROI −13.2% 送钱区** | **敞口敞开** |
| L4 冷(2.2-3.0) | n=169, ROI +1.2% 价值区 | 敞口敞开 |
| L5 深冷(≥3.0) | n=40, ROI −1.4% | 敞口敞开 |
| **合计** | n=954, ROI **−7.9%** | n=452, ROI **−6.8%** |

**闸门挡住了 L2，却完全没覆盖 L3——而 L3 同样是"送钱区"（−13.2%，n=243），
是当前活口径 −6.8% 的主要来源。** `odds_below=1.8` 这个边界正好切在 L2/L3 分界上。

三份外部建议都只盯着 L2，没人注意到 L3。

⚠️ **但不要直接改**：n=243 的 ROI 置信区间较宽，需先扩样本确认。
而且在第 5 节结论下，更根本的做法是**先决定要不要继续在竞彩价格上下注**
（12.1% 抽水 vs 模型 0.6% 相对优势，差 19 倍）。

## 7. 诚实的边界

1. **第 5 节测的是纯球队实力模型（DC），不是完整系统。** 完整系统当前是 93.75% 市场。
   结论应该读作：「模型层对决策有净负贡献，因此该取 0 权重」，
   而不是「整个系统没有价值」——一个 100% 市场的系统至少不会因为模型而变差。
2. **没有测试的信息源尚未被检验**：伤停、DJYY、xG、跨盘口一致性。
   这些恰恰是**模型之外**的信号，也是唯一可能有真 edge 的方向。
   数据已经就位（6.2 万场 + 33,060 场亚盘/大小球），只是还没接。
3. **联赛级结论已做 FDR 校正**，但 n=1,500~3,900/联赛，仍不足以支撑
   「按联赛配置资源」这类动作。
4. 全部为虚拟记账与算法研究，不构成任何投注建议。
