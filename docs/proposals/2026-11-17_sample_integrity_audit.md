### 2.2 机制：登录态一死，公开数据也一起停写（代码链）

`scripts/njstats_duty.py` 里有两条互相独立的耦合：

1. `njstats_duty.py:651-658`：mint 失败（站方 session 死）时 `return _code`，而四份快照的
   写入排在**它之后**（`:685-690` 调 `_maybe_server_records_snapshot()` / `_maybe_community_snapshot()`，
   strategies 同组）。维护者自己在 `:652-655` 注释里记下了这次事故：
   「2026-11-07 事故：……摘要就停在最后一次成功（实测停在 11-04 16:05、red_flags 为空长达 73 小时）」。
   与 §2.1 的断档区间吻合：`my_predictions/2026-11-04.json` 的 `snapshot_at` 正是
   `2026-11-04 16:05:22`，下一份文件是 `2026-11-08.json`（16:56）。
2. `njstats_duty.py:874-883`：`api.my_predictions()` 返回 `None` 时**整个函数 return**，
   而同一函数后半段（`:913-933`）写的是 `site_odds` 全板赔率——后者走 msgId=1，按
   `scripts/njstats_challenge/README.md:29/35` 是 **apikey 就能读的公开板**
   （「apikey 读得到一切，但提交永远『请先登录』」）。

合起来：**私有端点/登录态一挂，连不需要登录的三份公开快照也一起停写**。
`NJSTATS_JWT` 约 20h、站方 session 约 60 分钟空闲即死（`docs/CHALLENGE_SUBSYSTEM.md` JWT 节），
所以这不是尾部事件：实测 27 天里已经烧掉 4 天。

### 2.3 缺口的代价能不能补（已证实：补不回，但原因和注释里写的不一样）

站点板是 current-only——`njstats_duty.py:908-913` 的注释自己写明「站点赔率只在当前板可见，
赛后就变了，不存下来永远没法回测」，所以缺的那 4 天永远补不回来。
但**把日内序列补齐也换不来收盘价**（`--history` 实测，按「开赛前三天是否都有 ≥24 轮」分时代）：

| 注单所属时代（按开赛日） | 注数 | 最后一次上板距开赛 | 距开赛 ≤6h |
|---|---|---|---|
| 日内序列完整 | 27 | median **15.7h** | 4 注（15%） |
| 日内序列有缺口 | 30 | median 11.7h | 9 注（30%） |
| 只有当天最后一轮（赛日 ≤11-03） | 55 | median 28.2h | 0 注（0%） |

首次上板距开赛 median 52.4h ⇒ 可见窗口大约 T−52h → T−16h：**站点在开前十几个小时就把场次
移出可提交板**。这条给 §7-P2 定了价：日内留存能救回的是账目对账与赔率序列连续性，
**不是** CLV 收盘价；收盘价仍得走 `clv_pinnacle`（Pinnacle/fdc）那条链，
或者就用 records 里已经存下的下单价（§5.3 已证实它与服务端 100% 一致）。

## 3. 结算滞后（已证实：不是丢样本的主因）

### 3.1 可测窗口的滞后

口径：`lag = 该场比分第一次出现在 git 里的提交时刻 − results_sina.match_time`，是**上界**
（日文件历史只有 N 次提交时，比分可能在两次提交之间就已落本机盘，git 看不见）。
在池 112 注、赛日 ≥2026-11-03 的 **46 注**：median **3.2h**、p90 5.6h、max **10.1h**、>12h **0 注**。
逐赛日中位数（小时）：11-03 2.1｜11-04 4.4｜11-06 2.4｜11-08 4.5｜11-10 2.5｜11-12 3.0｜
11-13 2.9｜11-14 3.3｜11-15 2.1。⇒ 「结算滞后把注拖出判定期」在当前数据里**不成立**。

### 3.2 测不到的那一半（已证实的审计盲区）

**55/112 注（49.1%）** 赛日 ≤11-02，其 `data/daily/<day>/results_sina.json` 在 git 里只有
11-04 02:08 那一次批次提交 → 实测 lag 全落在 22.4–289.4h，那是**提交时刻**而不是结算时刻。
另有 11 注（9.8%，含未开赛的 5 注与 §4 那类无比分行）在 git 历史里找不到比分行。
后果：**E8/E10 冻结样本里将近一半的注，其结算时点无法事后审计**——谁在什么时候拿到比分、
有没有跨日回填，仓库里没有证据。修法见 §7-P3（把「未知」显式打在面板上，别让 lag 图看起来覆盖全程）。

### 3.3 pace 的 n 是「已提交」，不是「已结算」

`experiment_pace.summarize()` 用 `n=len(pool)`（已提交）判 `n≥60`，命中率/ROI 用 `judged`。
当前实况：**E10 打印「n=64/60｜已达 n=60，可按判据收尾」，而 judged=59**（5 注未结算，7.8%）。
E8：n=48、judged=48，无敞口。

这**不算改判据**：`docs/EXPERIMENTS.md` E8/E10 两行的到期条件写的就是「满 60 注（先到为准）」，
而且 11-16 的 E10 终判是按已结算 59 注算命中率、并对未结算注做过稳健性检查的（登记行原文：
「未结算 4 注即使全命中 p≈0.12 仍不达标」）。剩下的只是**读数歧义**，但它是**三个分母**：

| 面板上同一行的量 | 算在哪个集合上 | E10 当前值 |
|---|---|---|
| `n=64`（pace，判「满 60 可收尾」） | 已提交 | 64 |
| 命中率 69.5% / ROI +6.1% | 已结算 | 59 |
| **打平线 64.8%**（`pool_stats.break_even`，`challenge_reconcile.py:121`） | **已提交**（含那 5 注未结算） | 64.8% |

登记行写的打平线是 **65.2%**——那是只在 59 注已结算上算的（脚本同口径复现 = 65.18% ✓）。
也就是说：**同一个面板，今天重跑会把 65.2% 变成 64.8%，而没有发生任何数据修正**。
收尾/复核时若不写清用的哪个集合，终判数字无法逐位复现（漂移 0.34pp，在 p 值 0.289 这种
临界量级上不算决定性，但它是「复现不出来」而不是「复现成不同结论」）。

## 4. 让球走盘（口径不一致已证实；当前 0 注受损）

### 4.1 现状

`challenge_review.judge_hit`（`scripts/challenge_review.py:172-181`）对让球注：
`side=="home"` → `margin - line > 0`；`side=="away"` → `-margin + line > 0`。
整数线且 `margin == line`（走盘）→ 返回 **False**；`challenge_reconcile.pool_stats`
（`:121-130`）于是 `judged += 1`、`roi += 0*odds - 1` → **走盘既进命中率分母，又按全额亏损计 ROI**。
`tests/test_challenge_reconcile.py::test_handicap_walk_is_not_a_hit` 把「走盘不算命中」钉成了预期行为，
但那条测试只断言 `hits==0`，**没有断言它该不该留在分母里**——这两件事在代码里被合并成了一件事。

站点自己的口径是明确的（`scripts/fetch_njstats_strategies.py:59-63` field_notes，
2026-11-08 对站点 UI 零误差互验；另见 `scripts/njstats_api_submit.py:453-454`）：
`push` = 「走盘/退款场次」，`胜率 = wins/(total−push)`、`场均收益率 = profit/(total−push)×100`
——**退款并从分母剔除**。所以我方复盘对走盘的处理与结算方不一致。

### 4.3 顺带查出来的：8 注可能被判错了市场（已证实）

服务端 145 条真值注里，15 条记在非 1x2 市场码。本地怎么记的：

| 服务端市场码 | 条数 | 本地对应 | 判定实际用的口径 |
|---|---|---|---|
| 4 | 8 | pick 写成 `主胜@1.73` / `负@2.37` 这类，且**没有** `market` 字段 | `parse_pick → play=1x2` → 直接比 `actual_idx` |
| 4 / 5 | 5 | **本地完全没有这条注** | 无（就是 §5.2 的 5 条缺口） |
| 2 | 2 | `主队-1@0.95（让球实验）`、`客+0.5@0.95` | `parse_pick` 从 pick 认出让球 → **按比分+线判，判定是对的**；这两条老注单连 `market`/`sid` 字段都没有（11 条无 sid 的同一批），所以只能靠队名回挂 |

⇒ 那 8 注（马尔默 vs 卡尔马、都灵 vs 乌迪内斯、科里蒂巴 vs 博塔弗戈、第戎 vs 梅斯、莱万特 vs 塞维利亚、
法马利康 vs 艾华卡、KFUM奥斯陆 vs 瓦勒伦加、考文垂 vs 纽卡斯尔联）的命中/未命中，
**只有在市场码 4 == 胜平负时才成立**；而 `scripts/njstats_challenge/README.md` 只逆向到
「提交体第二参是市场码」，没有给码表。**推测**：码 4 很可能是竞彩胜平负（与码 1 的站点胜平负并列），
那样结论不变；但也可能是让球/比分——那就等于用错考卷判分。
这 8 注全在冻结池外，只影响 `challenge_review.json` 的跨周聚合（n_settled=133），
**不影响 E8/E10 的任何数字**；要定论只需要站点 UI 上任一场的玩法截图，成本极低（见 §7-P4 追加项）。

CI 只投 1x2（`challenge_hourly.py:312` 的 `api.submit(jwt, sid, 1, dir+1)`），所以
**冻结池里让球注 0 注、走盘 0 注 → 当前零污染**。但服务端真值 145 条注里有 **15 条是非 1x2
市场码**（码 4 × 11、2 × 2、5 × 2，全在 10-22 之前的 Air/手工期），这些注在本地 records 里
要么没有 `market` 字段、要么被写成 `"1x2"`（`challenge_hourly.py:316-318` 的注释已经承认：
「历史上有 5 条让球注被套用了这里的 "1x2"/None」）。也就是说：**一旦恢复让球提交，
按站点自身 4.6%–17.1% 的走盘率，每 6–20 注就有 1 注被记成「输掉一整注本金」**；
在 E10 那种 60+ 注量级、ROI 只有 +6% 的口径下，这足以把结论从「方向为正」推到「负」。
现在它还没发生 ⇒ 属于预登记范围，不是本轮可以顺手改的东西（改 `judge_hit` = 改判定口径）。

## 5. 服务端真值 vs 本地 records

### 5.1 「我已预测」列表被分页截断（已证实）

`njstats_api_submit.my_predictions()`（`scripts/njstats_api_submit.py:370-379`）固定
`page=1, size=60` **且不翻页**（`:375`），而它的 docstring（`:329`）写着
「有效 JWT 返回本账号**全部**已预测场次」。快照序列自己把矛盾显示出来了：

```
10-21 33 → 10-22 41 → 10-23 47 → 10-24 56 → 10-25 59 → 10-26 60 → 之后 19 份快照恒为 60
（同期本地 records 从 60 涨到 140）
```

而且是**按提交时间截断的最近 60 条**，不是随机丢：最新快照里可见的本地注单时间范围
`2026-11-01 13:05:13 → 2026-11-16 19:05:13`，被挡在外面的最后一条是 `2026-11-01 03:24:18`
——60 条切口两侧的时间严格相邻。两个直接后果都落在生产代码上：

1. **跨机去重**（`challenge_hourly.py:193-217`）把这份列表当权威去重名单。现在它只覆盖
   本地 sid 注单的 46.5%。今天风险有限（板上的赛期只到 T+2，而被截掉的最后一注提交于
   `2026-11-01 03:24:18`，早已完赛），但失效方式是**静默的**：`_extra` 只在有条目对不上时打印，
   且打印的是「服务端已预测 N 条」这种看着正常的数字。
2. **对账行**（`challenge_reconcile.snapshot_line()`，`:154-174`）只遍历快照里可见的服务端条目，
   方向单一（服务端→仓库）。本轮实测输出是
   `账目: 快照 60 条/0.2h vs 仓库 140；仓库未记 0 条：无`
   —— **在真值只剩 43% 覆盖度的那天，看板写着「无缺口」**。反向（仓库有、服务端没有=幽灵注）
   从来没被计算过（本审计算出来是 0 条，见 §5.2）。

### 5.2 双向差额（已证实）

### 5.3 下单那一刻的站点价（已证实：完全一致）

## 6. 到期后仍在收注（新增一轴，已证实）

E10 的登记判据是「2026-11-22 或满 60 注（先到为准）」。实测：

- 第 60 注提交于 **2026-11-16 17:05:13**，而**同一轮一起投了 4 注**（都盖着这个时间戳）
  ⇒ 池子从 59 直接跳到 63。这就是登记行写「63 注」而阈值是 60 的原因——`K=6` 的批量提交
  天然会冲过阈值，不是有人多投。
- **19:05:13 又进 1 注**（法罗群岛 vs 摩尔多瓦，体彩价 1.55，`exp="E10"`）。
- 护栏⑤的价筛回退（`challenge_policy.min_sporttery_odds: 0.0 → 1.6`）由 PR #103 落地，
  commit `4f94f2dbb` 时间 **2026-11-16 19:08**——比那注晚 3 分钟。

机制：回退是「改 policy 文件 + 上游 PR 合并」，而闸门每小时从仓库读一次 policy。
从「判据到期」到「回退真的生效」之间必然存在一个（合并耗时 + 最多 1 小时）的窗口，
期间的注会继续进**已终判**的池子。本轮代价：1 注（E10 复算 n=64 vs 登记 63），
不改变 E10 的终判（判据已按 59 注已结算样本定，且登记行写了稳健性）。
但「仓库能复算出的池」与「登记表里的池」从此永久差 1 注，任何后续复核都会先撞在这个不一致上。
