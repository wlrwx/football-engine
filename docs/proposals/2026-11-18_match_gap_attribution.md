## 0. 结论（三句）

1. **「池子上百场、只匹配 5~7」主要不是丢失，是分母不同层。** 25 张池子快照里
   **92.5%** 的板面条目在那一刻结构上不可能匹配：45.2% 开球在 D+2 之后（预测还没生成）、
   25.5% 在竞彩开售名单里找不到任何证据、21.8% 站点没给 1x2 三档价。
2. **匹配口径本轮无可行动发现。** 按「快照 × 当轮可加载预测」的条次算，
   扣掉「已投过」和「快照时已开赛」后可投 388 条次里生产匹配 **91.0%**、
   队名别名只丢 **1.6%（6 条次）**、站点板上没这场 **7.5%（29 条次）**；
   而这 6 条按冻结闸门重放 **0 场本可合格**。与 PR #107「译名红利已吃完」的结论一致，
   两条独立路径互相印证——**不建议再为匹配面动任何东西**。
3. **可行动的两处都在采集面**：板面快照 25 张里 20 张落在 23:35–23:36（时刻偏置，见 §4），
   以及每轮的 `池/匹配/候选/最高ev` 只活在本机 `duty.log`（云端无法源码复查，见 §5-C）。

## 3. 预测侧与销售日覆盖侧（自家漏斗，两个分母）

**预测侧**（分母 = **条次**：每条预测会在 D-1、D 两张快照里各被加载一次，
所以 581 条次对应 345 条唯一预测；比率描述的是「一轮里看到的样本长什么样」，不是场次去重）：

| 桶 | 条数 | 占比 |
|---|---|---|
| `1_matched_production` | 353 | 60.8% |
| `2_already_submitted` | 100 | 17.2%（服务端真值里已投过，本就该跳过） |
| `3_kickoff_already_past` | 93 | 16.0%（快照 23:35 时已开赛/不足 45 分钟） |
| `6_not_on_pool_board` | 29 | 5.0%（站点板上找不到任何相似场次） |
| `4_alias_recoverable` | **6** | **1.0%** |

扣掉不可投的两类后**可投 388 条次：匹配 91.0% / 别名丢 1.6% / 板上没这场 7.5%**。

**销售日覆盖侧**（分母 = 该销售日竞彩开售场数，赛果∪预测按异写并簇后计数）：

```
开售 380 → 落库预测 345（90.8%）→ 被池子匹配上 283（占开售 74.5%、占预测 82.0%）
  ▸ 2026-11-09 开售  0 预测  0   ← predictions.json 没落库（且该日无赛果，见 §5）
  ▸ 2026-11-16 开售 30 预测  8   ← 唯一一次大面积预测缺口（22 场）
  ▸ 2026-11-18 / 11-19 开售 0 预测 0 ← 新北京日时序空窗，不是数据洞（PR #101 已就这点修过摘要判据）
```

这一层的量级比匹配层大：竞彩开售的 380 场里约九成（345）落了预测，
预测里 82.0%（283）在有快照的那些时刻被池子匹配上。剩下 62 场只能给出**形状**、给不出可加的分解：
上面预测侧那张表把同一条预测在 D-1、D 两张快照里各数了一次（581 > 345 就是这个原因），
其中确认「板上找不到相似场次」的 29 条与「译名丢」的 6 条是两种形状，不能与 62 直接相减。
**其余为什么没匹配上，现有数据归不出来**——4 天缺快照、且每天只有一张 23:35 的板面，
那一刻已开赛的场次无法区分「站点没开盘」和「没赶上时刻」。
这正是草案 B/C 要补的观测缺口，不是匹配逻辑的问题。

## 4. 交叉核对：日志说的「匹配 5~7」与本表为什么不矛盾

本机 `~/.football-engine/duty.log`（未入库；窗口 2026-11-11…11-18，312 轮 / 8 天）：
**304/312 轮（97.4%）单轮匹配数 ≤7**，每日匹配峰值中位 8（区间 0–12），每日池最大值中位 191。

本 PR 的日均 14.1 场更高，是口径不同——这是**回看上限**：把 D、D+1 两个销售日的落库都算进来。
353 场匹配里只有 **95 场**的预测来自目录 D，**258 场来自 D+1**，
而 D+1 的预测通常次日凌晨 00:09–03:12 才落库（`git log --diff-filter=A` 抽查 6 天）。
23:35 那一刻生产拿不到 D+1，所以单轮日志必然低于本表。
**结论：拿 §2/§3 的数与 duty.log 直接比是错的**；这个坑只能靠 §5-C 的采集改进消掉。

另外，板面快照本身有 80% 落在 23:35–23:36（25 张里 20 张，其余 00:05/03:01/16:05/17:35/21:35），
所以「当天下午/晚上开赛前还能不能投」这类问题，现在的仓库数据回答不了。

## 5. 已证实 / 推测

**已证实**（复现命令见 §1；逐条证据在 `--json` 的 `alias_evidence`、`coverage.per_day`）：

1. **译名丢失已被 PR #107 基本清空（同窗口前后对拍）**。同一个 23 张快照窗口
   （2026-10-21…11-16），在 #107 之前的 base 上跑本脚本 =
   **匹配 302 场 / 别名可挽回 27 场 / 15 条映射**；换到含 #107 的 base
   （`upstream/main` = 452d7a39）重跑 = **匹配 351 场 / 别名可挽回 6 场 / 5 条**。
   即 #107 那 12 对补录在这 23 天里真实救回 **49 场匹配**（+16.2%）。
   剩下 5 条：`浦和红宝石→浦和红钻`(3 天)、`墨尔本胜利→墨胜利`、`奥摩尼亚→奥莫尼亚`、
   `维特斯→维迪斯`、`马斯特里赫特→马斯特里`。
2. 这 6 场按冻结闸门重放（`ev_floor=2%`、上界 25%、`min_sporttery_odds=0.0`，参数**只读**自 policy）
   → **0 场本可合格**。对照：生产匹配上的 353 场有 132 场（37.4%）本可合格。
   即：现在再补别名，对本窗口的注数与 EV 都没有可测收益。
3. **站点覆盖是硬约束**：可投预测里 7.5%（29 条）在板上根本找不到相似场次；
   池子侧 25.5%（1655 场）在竞彩开售名单里找不到证据。两侧同向。
4. **`predictions.json` 真数据洞只有一个**：120 个销售日目录里缺 3 天，其中
   11-18/11-19 是新北京日的时序空窗（PR #101 已把这类从告警里摘出去），
   真正丢的是 **2026-11-09**（当天 `import_manifest.json` 记 `fixture_count=11`，却没落 predictions）。
   11-16 则是「落了但只有 8 条而开售 30 场」的大面积缩水（§3）。
   `challenge_hourly.py:183-184` 对缺文件只是 `continue`，日志里只会留下一个无法归因的 `匹配0`。
5. **快照有 4 天洞**（10-31、11-05、11-06、11-07）→ 这些天完全无法归因。

**推测（本 PR 不背书）**：

- 「`10_no_sporttery_evidence` 全是站点独有联赛」——只能说仓库里没有竞彩开售的证据，
  证实需要竞彩官方开售名单（没落盘）。
- 「`8/9_sold_not_predicted`（8 场）是预测管线过滤造成的」——样本太小，没查 `engine/main.py` 筛选链。
- 「中午加一张快照后别名/覆盖结论不变」——需要按 §6-B 的判据实测两周才能确认。

## 7. 采集改进草案（本 PR 一条都没实施；判定方法写在每条里）

**A. 不建议现在动匹配面。** 残余 5 条映射（`浦和红宝石/浦和红钻` 等）在本窗口重放里
**0 场本可合格**，收益为零；若以后要补，按 #107 的收敛式扫描（`alias_gap_scan.py` 迭代到归零）
而不是按本脚本的清单，且需 E8/E10 负责人同意并人工登记。本 PR 不新增别名。

**B. 每天再加一张白天板面快照**（放 `data/state/njstats/site_odds_midday/<D>.json`）。
- 收益：现在归因几乎全部基于 23:35 那一刻，当天下午/晚间场全落进
  `2_kickoff_too_close`(120) 与预测侧 `3_kickoff_already_past`(93)，而不是它们的真实归属。
- 判定：①两张快照各跑本脚本，`2_kickoff_too_close` 与 `3_kickoff_already_past` 应显著下降；
  ②`5_alias_recoverable` 两口径之差 ≤2 场/天，否则本文 §5 的结论要重做；
  ③缺天率 ≤1/30。
- 兼容性（**已逐个查过消费者，别用带后缀的文件名**）：`engine/sources/njstats_side.py:145-150`
  在 `date=""`（默认值）时是 `glob("*.json")`，`site_odds/<D>-12.json` 会被一并读进侧挂特征、
  同一场比赛出现两份板面；`scripts/challenge_reconcile.py:145-148` 用 `{p.stem}` 对 ISO 日期做
  缺失对账，带后缀文件会被静默忽略；`scripts/ops_digest.py:356` 的红线只认 `site_odds/<今天>.json`。
  所以：**新快照放独立子目录**，并把该目录加进 `scripts/njstats_duty.py:57` 的 `SNAPSHOT_PATHS`；
  **主快照不许改名**。体积：现 25 份 = `du -sh data/state/njstats/site_odds` → **820K**（约 33K/天），
  每月多约 1MB，远低于 `scripts/check_repo_size.py` 的 5MB 单文件门禁。

**C. 每轮把 `池/匹配/候选/最高ev/合格数` 落到仓库**（`data/state/njstats/round_funnel/<D>.jsonl`，
一行一轮）。现在这些数只在本机 `duty.log`——`scripts/challenge_reconcile.py:11-12` 早写明这是
CI 侧「拿不到的一块」，本 PR 的 §4 也只能靠登本机读日志才做成。
- 判定：落地后，在没有 `duty.log` 的机器上（CI、别的工单目录）也能复现 §4 那句
  「304/312 轮 ≤7」；届时本脚本改成读这份 JSONL 而不是 `--duty-log`。
- 代价：约 48 行/天，体量可忽略；但新增写盘路径，需人确认不与 ci-sync 抢写。

**D. daily-forecast 收尾断言当天 `predictions.json` 存在且非空**（针对 §5-4 的 11-09 型洞）。
断言必须排除「新北京日空窗」（PR #101 的规则： manifest 都没有才算洞），否则每天误报。
**本 PR 不实现**：要动 CI 判定链，属另一个工单。

## 8. 局限

- 快照窗口 25 天、缺 4 天；duty.log 窗口只有 8 天 312 轮（日志会轮转）。
- 别名可挽回样本 6 场——**远小于能支撑比例推断的量**，所以本文只说「收益测不出来」，
  不说「补了会掉 EV」。
- `kickoff` 字段在预测落库里缺 72/1538 条（4.7%）；缺时刻的条目最多只能进
  `6_alias_unconfirmed`（疑似，不计可挽回）。本轮该类实测 0，说明这 4.7% 没掩盖额外的可挽回别名，
  但这只在 25 天窗口内成立。
- 销售日与开球日的关系（开球落在 D 的 577 场、落在 D+1 的 889 场，没有 D-1 或 D+2）
  是当前采集链的经验分布；若竞彩改变开售节奏或站点延长板面窗口，§2 的 45.2% 会变。
- 池侧的「无证据显示竞彩开售」与「站点覆盖不足」是同一件事的两个方向，
  两者都不是本仓库能修的（要厂方数据或别的赔率源）。
